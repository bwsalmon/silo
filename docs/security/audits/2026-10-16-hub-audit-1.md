# Security audit 1: the Silo hub on `main` (2026-10-16)

An audit of the Silo hub as it is on `main` at `cc10a38`, against the
invariants (`INV-n`) and threats (`T-…`) of
[threat-model.md](../../threat-model.md). This audit reports findings
and does not fix them. Each critical, high and medium finding has a fix
task, and the low findings share one; the closing note on task 4271
lists the task numbers.

- **Scope:** `hub/*`, `internal/*` (`tunnel/mux`, `fakeoidc`,
  `pgtest`, `testlog`), `events`, `cmd/silo` (`silo hub serve`, `team`,
  `token`), `Dockerfile`, `deploy/**` (the kustomize base and the
  `bsalmon-gke-dev` overlay, `validate.sh`, terraform), and
  `.grain/workflows/*`. Grain's side (`pkg/hubnode`, `pkg/policy`) is
  out of scope, except where a hub finding depends on what a Grain
  does.
- **Method:** I read every non-test line of the scope. I ran the test
  suite (`go test ./hub/... ./internal/... ./cmd/...`: every package
  `ok`) and `govulncheck ./...` (govulncheck@latest, local toolchain
  go1.26.6). Where a finding needed proof, I wrote a throwaway exploit
  test and ran it against this tree. Those tests are not committed;
  each one is attached to its fix task.
- **Not covered:** the deployed configuration (nothing is applied to a
  project yet: IAP's access list, the backend services, and the IAP
  cookie's attributes are §8.3 items); the hub UI, which is not built;
  and a black-box run from outside.

## Findings

### SA1-H1 (high): node-ID-bound task paths survive the node changing hands

**Where:**
- `hub/tasks/dispatch.go:231` (`case t.State == Lost && d.reachable` → `start(…, TypeResume)`)
- `hub/tasks/dispatch.go:237` (cancel)
- `hub/tasks/dispatch.go:499` (opens the stream to `t.Node` and writes the whole `Spec`, prompt included)
- `hub/tasks/dispatch.go:345` (`admit` is only on the offer path)
- `hub/directory/tokens.go:62` (`MintNodeToken` only refuses a node ID another owner holds a *live* token for)
- `hub/directory/access.go:44` (a node listing no repositories is admitted with no team check)
- `hub/live/hub.go:302` (an event stream is accepted if `task.Node == nodeID`)
- `hub/live/http.go:234` (an artifact view opens `t.Node`)

**What:** A task records only the node *ID* it was placed on. The
binding of a node ID to its owner lives in two places. The in-memory
registry (`registry.ErrOwner`) forgets it on every restart, and every
rollout is a restart, since the Deployment is `Recreate`. The token
table forgets it as soon as the owner's tokens are revoked. After both
have happened, any signed-in human can `POST /v1/node-tokens
{"node":"<that id>"}` and connect with no repositories, which `Admit`
lets through. The dispatcher then sends that node the `resume` of every
lost task recorded on the ID, carrying the full spec (title, prompt,
submitter, team, repository). The node can accept it, stream lifecycle
and conversation events into the victim task (they are stored), finish
it `done` with a forged reason, answer the task's artifact views with
content of its choosing, and receive the deliveries of pending cancels.

Even without the ID changing hands, the resume path never re-runs
`admit`. An owner removed from the task's team while their node was
away is still handed the task when the node comes back, provided it
reconnects listing no repositories (or only repositories it is still
admitted for). INV-7 says "at every offer", and a resume is an offer
of the same spec.

**Reproduction** (throwaway test, attached to the fix task;
`hub/tasks`):
1. alice (team infra) has a task running on `ws-1`. Her node drops,
   and the task is `lost`.
2. The registry forgets `ws-1`: `Registry.Forget`, equivalent to a hub
   restart.
3. mallory (team web only) connects as `ws-1` with `Repos: []`.
   - Result: she is sent `resume` with infra's prompt, accepts, and
     reports `done`, and the task finishes `done` with her reason.
4. Separately, alice is removed from infra while her node is away. Her
   node reconnects with no repositories.
   - Result: it is still sent the resume.
5. In `hub/directory`: alice mints `ws-1` and revokes it.
   - Result: mallory's mint of `ws-1` succeeds.

All three tests pass on `cc10a38`.

**Preconditions:** the original owner's tokens for the ID are revoked
(the owner decommissioned the node, or an admin revoked a departed or
compromised user's tokens) while a task on it is lost or has a cancel
pending, and the hub restarts. The attacker is any user IAP admits,
with no team membership needed.

**Violates:** INV-5 (registered "never under an ID another owner
registered"), INV-7, INV-8 ("a task the hub has placed on that same
node"), and T-TB1-2 (A-6 to another team).

**Fix:**
1. Record the node's *owner* on the task when it is offered (a
   `node_owner` column), and on resume, cancel, event-stream binding and
   artifact view require `Registry.Get(t.Node).Owner == t.NodeOwner`.
   On a mismatch, treat the node as a different node: do not resume,
   and requeue after the team's grace.
2. Call `d.admit` (filtered to the task's repositories) before a
   resume, as the offer path does, and requeue on refusal.
3. Keep a node ID bound to its first owner permanently, across
   revocation, until that owner or a hub admin explicitly releases it.
   `MintNodeToken` should refuse an ID with *any* token row of another
   owner. Alternatively, namespace node IDs by owner.
4. Add regression tests mirroring the three exploit tests.

### SA1-H2 (high): a node can exhaust the hub's memory through the mux

**Where:**
- `internal/tunnel/mux/mux.go:416` (every ping spawns `go writeFrame(FramePong, …)` holding its ≤ 64 KiB payload)
- `mux.go:418` (any pong, solicited or not, refreshes `lastPongTime`)
- `mux.go:445` (a reset per refused stream, also `go`)
- `mux.go:401` with `mux.go:47` (a peer whose first frame is not a window update is "legacy": no flow control, and each stream may buffer `legacyMaxBuffer` = 16 MiB)

**What:** The hub's `rwc` (the WebSocket) has no write deadline, so
when the node stops reading, every pong writer blocks on `writeMu`. A
node that sends pings and never reads makes the hub hold one goroutine
and one payload copy per ping, with no bound. Its own unsolicited pongs
keep the ping timeout from ever firing. Separately, the threat model's
mitigation "the mux has per-stream flow control" is the peer's choice.
A peer that opens without a window update gets 16 MiB per stream
instead of the 1 MiB window, on every stream the hub is slow to read: a
view to a slow viewer, a node UI response, a stream that never writes
its first line (O-5). The hub is one replica with a 512 MiB limit
(`deploy/kubernetes/hub/base/deployment.yaml`). An OOM kill drops
every tenant's nodes, subscriptions and in-flight offers, and the
attacker can repeat it at will. Minting a node token needs only an IAP
sign-in.

**Reproduction** (throwaway tests on a `net.Pipe`, attached):
- 2000 pings of 64 KiB, with one unsolicited pong per 100, to a server
  mux whose peer never reads, leave 2000 goroutines parked and 144 MiB
  of heap in use, and the session is still open after more than four
  ping intervals.
- A peer whose first frame is data buffers 16 MiB unread on one stream.

**Violates:** INV-19 (everything a node sends is bounded) and T-TB2-7
(A-10). This is more concrete, and cheaper for the attacker, than the
open O-5.

**Fix:**
1. Answer pings from one writer with a bounded control queue: coalesce
   or drop pings while a pong is pending, and close the session if the
   queue overflows.
2. Count only a pong whose payload matches an outstanding ping.
3. Put a write deadline on the session's `rwc` (close the session when
   a frame cannot be written within, say, the ping timeout).
4. On the hub (`IsServer`), refuse legacy peers: require the window
   update first, or treat a legacy peer as a 1 MiB-window peer and
   reset on overflow.
5. Add a per-session cap on buffered bytes and on open streams (with
   O-5).

Keep `mux` and grain's copy in step (T-TB9).

### SA1-M1 (medium): node UI hosts can forge hub requests as their owner

**Where:**
- `hub/identity/oidc.go:259` (`SameSite: Lax` session cookie)
- `hub/nodeui/nodeui.go:210` (a node's UI is served at `<node>.<NodeUIDomain>`, by default `nodes.<hub domain>`)
- every state-changing route in `hub/directory/api.go` and `hub/tasks/api.go`; none checks `Content-Type`, `Origin` or `Sec-Fetch-Site`

**What:** A node's UI host is a different *origin* from the hub, which
is what INV-13 relies on, but it is the same *site*. SameSite cookies
(the hub's OIDC session, and IAP's) are sent on requests from a node UI
page to the hub. The JSON decoders accept a `text/plain` body, so a
"simple" cross-origin `fetch(…, {method:"POST", credentials:"include",
mode:"no-cors"})` from a node UI page reaches the hub as its viewer
without a preflight. The node UI is shown only to its owner, but its
content is the Grain's: customised code, or a Grain compromised through
a host sandbox (T-TB7). Such a page can file tasks into every team the
owner is in, cancel and requeue the owner's tasks, mint and revoke the
owner's node tokens, administer the owner's teams, and, for a hub
admin, create and delete teams. The responses are unreadable, but the
writes land. O-1 is the general CSRF finding. This one adds that a fix
keyed on `Sec-Fetch-Site: cross-site` would still admit these requests,
because they are `same-site`.

**Reproduction:** by construction. A page on `ws-1.nodes.hub.example`
doing `fetch("https://hub.example/v1/tasks", {method:"POST",
credentials:"include", mode:"no-cors", body:'{"team":"infra","prompt":"…"}'})`
is sent with the hub's cookies (same-site), carries `Content-Type:
text/plain`, and is accepted by `readJSON`.

**Violates:** INV-16. It also weakens INV-13's purpose ("one node's UI
cannot script the hub's API").

**Fix:** with O-1, on every `POST`/`PUT`/`DELETE`:
- require `Content-Type: application/json`;
- require `Sec-Fetch-Site` to be absent (a non-browser) or
  `same-origin`, not merely "not cross-site";
- refuse an `Origin` that is not the hub's own.

Put the node UI domain on a different registrable domain than the hub
where possible (docs/deploy.md), and say so in hub.md §11.

### SA1-M2 (medium): repositories are claimed first come, first served

**Where:**
- `hub/directory/api.go:287` (`assignRepo`, any team admin)
- `hub/directory/store.go:377` (`AssignRepo` refuses only a repository another team owns now)
- `store.go:250` (`DeleteTeam` leaves its repositories unowned)
- `hub/directory/access.go:120` with `hub/tasks/api.go:100` (`sees`: visibility follows the current owner)

**What:** Nothing ties a repository to a team except who claims it
first. Any team admin can claim any `owner/name` that is unowned at
that moment: never assigned, released for a transfer, or left behind
by a deleted team. Doing so:
- shows the claimer's team every past task of that repository, with its
  prompts, conversation and stored events, because `sees` follows the
  current owner;
- makes the claimer's members' nodes eligible for the repository's
  future tasks;
- blocks the rightful team, whose `PUT` now answers 409.

T-TB1-2(a) accepts history following a *deliberate* transfer, but not
a claim by an arbitrary team admin. Team admins are delegated (any
team admin can make anyone an admin), so in practice this is any user
a team has made admin.

**Reproduction:**
1. Team `a` owns `org/x` and has tasks on it. A hub admin deletes `a`,
   or `a` releases `org/x` to hand it to team `b`.
2. An admin of an unrelated team `c` sends `PUT
   /v1/teams/c/repos/org/x` before `b` does.
   - Result: `c`'s members can `GET` every one of `org/x`'s tasks and
     their events, and `b` gets 409.

**Violates:** INV-9 (sees a task "as a member of … the team owning its
repository", where ownership was never established) and INV-7.

**Fix:** make repository assignment a hub admin action, or let a team
admin claim only repositories under forge owners a hub admin has
granted to that team. Alternatively, require proof of forge access
(for example, a Grain of a team member that can read the repository).
On a release or team deletion, keep the old tasks visible only under
the team recorded on the task, unless a hub admin transfers them with
it. Add an audit-log entry (O-10).

### SA1-M3 (medium): the hub forwards any ref to the node for a view

**Where:**
- `hub/live/http.go:224` (`serveArtifact` checks only `validRef`: printable and ≤ 512 bytes)
- `hub/live/classify.go:280` (`validRef`)

**What:** Any member of the task's team can ask
`/v1/tasks/{id}/artifacts?ref=<anything>`, and the hub writes that
`ref` to the node holding the task. Refusing refs the Grain never
listed is left entirely to the Grain (INV-11, whose view half is an
untested gap on grain's side). A Grain whose view handler joins `ref`
to a path, for example `../../.git-credentials` or
`../sandbox-env/…`, hands A-1 and A-2 of the node's *owner* to any
other member of the team. The hub knows which refs the node announced,
because each one passes through `Classify`, but keeps them only in the
token ring.

**Violates:** INV-11 (defence in depth on the hub side), and A-2 via
TB4.

**Fix:** have the hub keep, per task, the set of refs the node listed
in its artifact events (refs only, which are already ≤ 512 printable
bytes; store them with the task or in the event store as a lifecycle
row), and answer 404 to a view of any other ref. Add a conformance
case (task 4236) that a Grain refuses an unlisted ref and a `..` ref.

### SA1-L1 (low): open redirect after OIDC sign-in

**Where:** `hub/identity/oidc.go:265` (`localReturn`).

**What:** `/auth/login?return=%2F%09%2Fevil.example` passes
`localReturn`, because the value starts with `/` and not with `//` or
`/\`. `http.Redirect` cannot parse a URL with a control character, so
it writes the value raw as `Location: /\t/evil.example`. Browsers strip
the tab and follow `//evil.example`. The redirect happens right after
a successful sign-in, which suits phishing. This applies only in OIDC
mode, not behind IAP.

**Reproduction:** a throwaway test (attached) shows `localReturn` and
`http.Redirect` passing `/\t/evil.example` and `/%09/evil.example`
through unchanged. `\n` is turned into a space by net/http.

**Fix:** refuse any control character or `\`, and accept only a value
that parses as a URL with no scheme and no host, whose path starts
with a single `/`.

### SA1-L2 (low): re-minting does not end the old token's connection

**Where:** `hub/directory/api.go:325` (`mintToken`); `tokens.go`
(`MintNodeToken` revokes earlier tokens in SQL only).

**What:** T-TB2-5 offers "minting again revokes the earlier token" as
the recovery for a stolen token, but the thief's live connection
stays. It is ended only when the legitimate node reconnects with the
new token, which supersedes it, or by an explicit `DELETE`. If the
owner's node is down, the thief keeps receiving the owner's team's
offers.

**Fix:** call `Disconnect(node)` after a mint that revoked any token,
as `revokeToken` does at `api.go:355`. Test it through `directory.API`
(INV-6's gap).

### SA1-L3 (low): node-supplied strings in logs

**Where:**
- `hub/live/hub.go:303`: `"task %s is not on node %q"`, where `e.Task` is node-controlled and unquoted, up to 1 MiB.
- `hub/live/hub.go:316`: the same with `%s`.
- `hub/rendezvous/server.go:295` and `hub/tasks/dispatch.go:611`: an unknown message type, `%q` but up to 1 MiB, once per line.
- `hub/tasks/dispatch.go:588`: the reason (O-7).

**What:** A node can forge log lines with newlines in `e.Task`, or
flood the logs at up to 1 MiB per line.

**Violates:** INV-18 ("node-supplied strings it logs are truncated and
quoted").

**Fix:** one helper that quotes and truncates (for example to 200
bytes) every node-supplied string, used at each site, and a log-capture
test.

### SA1-L4 (low): known vulnerabilities in the toolchain and x/net

**Where:** `go.mod` (`toolchain go1.26.9`, `golang.org/x/net
v0.59.0`); `Dockerfile:11` (`GOTOOLCHAIN=local` on `golang:1.26-bookworm`).

**What:** govulncheck at go1.26.6 (the sandbox's and grain CI's
toolchain, since `GOTOOLCHAIN=local` ignores the `toolchain` line)
reports 9 reachable stdlib vulnerabilities, all fixed in go1.26.9:
GO-2026-6617, -6613, -6612, -6611, -6610, -6608, -6607, -6605 and
-6603 (HTTP/2 server races and memory, HTTP/1 CONNECT desync,
textproto memory-limit bypass, ECH). Separately, x/net v0.59.0 has the
x/net halves of -6617, -6612, -6611, -6610 and -6603, fixed in
v0.60.0. The image's Go version is whatever `1.26-bookworm` resolves
to on the build host, so a cached old builder ships an old stdlib. The
hub serves HTTP/1.1 behind the load balancer, which limits exposure to
the HTTP/1 and textproto items.

**Fix:** pin the builder to `golang:1.26.9-bookworm@sha256:…`, or drop
`GOTOOLCHAIN=local` so go.mod's toolchain line applies. Bump x/net to
v0.60.0. Run `govulncheck` in `hub.yml`.

### SA1-L5 (low): no NetworkPolicy

**Where:** `deploy/kubernetes/hub/base/` has none.

**What:** Every pod in the cluster can reach the hub pod's 8080 (every
route, without IAP's own checks such as context-aware access, so a
leaked assertion can be replayed from inside the cluster, which
compounds O-2), its metrics on 9091, and the Cloud SQL proxy's health
server on 9090 (`--http-address=0.0.0.0`). The dev cluster is shared.

**Fix:** add a default-deny ingress NetworkPolicy. Allow 8080 from
Google's load balancer and health-check ranges (`35.191.0.0/16`,
`130.211.0.0/22`) and 9091 from the managed Prometheus collector only.
Bind the proxy's HTTP server to `127.0.0.1` and point the probe at
it. Check all of this in `validate.sh`.

### SA1-L6 (low): groups and emails share one principal namespace

**Where:** `hub/directory/api.go:63` (`isHubAdmin` matches `HubAdmins`
against emails *and* groups); `hub/directory/access.go:89` (`Access`
looks up email and groups in the same `team_members.principal`).

**What:** A group claim named like an email (`alice@corp.example`), or
like a group a hub admin listed, grants that membership or hub admin.
This is safe with IAP, which sends no groups, and with an identity
provider whose group names are admin-controlled. It is not safe with
one where users can create or rename groups that appear in the
`groups` claim.

**Fix:** store and configure groups as `group:<name>` and emails as
`user:<email>` (IAM style), and match each only against its own claim.

### SA1-L7 (low): missing server and session timeouts

**Where:** `hub/server/server.go:417` (only `ReadHeaderTimeout`);
`hub/rendezvous/server.go:381` (`Shutdown` writes goodbyes in
sequence, and each blocks on a node that does not read).

**What:** A client can hold a request body open indefinitely. One node
that stops reading stalls the goodbyes to every node after it, so
`Shutdown` overruns its grace and the pod is killed rather than
draining.

**Fix:** set `ReadTimeout` on non-streaming routes (or a per-handler
`http.MaxBytesReader` plus `ResponseController.SetReadDeadline`) and an
`IdleTimeout`. Send goodbyes concurrently, each with a write deadline
on the session (see SA1-H2).

### SA1-L8 (low): wider cloud privileges than needed

**Where:**
- `deploy/terraform/hub/main.tf:132`: `roles/cloudsql.client` on the project, so the hub can connect to every instance in it.
- `main.tf:106`: the hub's built-in user is in `cloudsqlsuperuser`.
- `main.tf:150`: `roles/iap.httpsResourceAccessor` on *every* IAP resource in the project until `iap_backend_service` is set.

**Fix:**
- Condition the `cloudsql.client` binding on the instance's resource
  name.
- Run migrations as one role and serve as a least-privileged role that
  owns only the hub's tables.
- Make the project-wide IAP grant opt-in, or apply in two steps so it
  never exists.

### SA1-L9 (low): a non-numeric `USER` with `runAsNonRoot`

**Where:** `Dockerfile:23` (`USER nonroot:nonroot`);
`deploy/kubernetes/hub/base/deployment.yaml` (`runAsNonRoot: true`, no
`runAsUser`).

**What:** The kubelet cannot verify that a named user is non-root and
refuses to start the container ("image has non-numeric user").
distroless's `nonroot` tag already sets 65532. This is a deploy
correctness bug that blocks INV-20's "containers run nonroot" from
being met in practice.

**Fix:** `USER 65532:65532`, or `runAsUser: 65532` in the pod spec.
Add a check to `validate.sh`.

### SA1-L10 (low): unauthenticated database work on the IAP-off path

**Where:** `hub/directory/tokens.go` (`VerifyNodeToken`) behind the
IAP-off `/v1/nodes/connect`.

**What:** Any internet client can make the hub run one indexed
`SELECT` per request by sending `Authorization: Bearer silo-node_x`.
There is no rate limit, so this is a cheap amplification against the
database pool the whole hub shares.

**Fix:** reject tokens that do not match the token's exact shape
(prefix, 16 hex characters, `_`, 43 base64url characters) before
hashing. Put Cloud Armor rate limiting on the nodes' backend.

### SA1-L11 (low): unbounded human-supplied fields

**Where:** `hub/tasks/api.go` (`cancel`: the reason is bounded only by
the 320 KiB body); `hub/tasks/task.go` (`Constraints.Labels`: count and
value length unbounded).

**Fix:** cap the cancel reason (for example at 1 KiB) and labels (for
example 32 labels of 63/255 bytes, Kubernetes-style), with O-5 and
O-7.

### SA1-I1 (info): subscriptions are not re-authorised

`hub/live/http.go:92`: access is checked when a subscription opens and
not again. A viewer removed from the team keeps receiving the task's
events, token stream included, until the task ends or the connection
drops (IAP's backend timeout is 3600 s). This is documented and
accepted (T-TB1-2c). I recommend re-deciding it with the hub UI: a
recheck every keepalive (15 s) would close it.

### SA1-I2 (info): unpinned inputs to CI jobs that hold read capabilities

`.grain/workflows/grain-interop.yml` builds and runs grain `main` HEAD
in a job with `repo-read:bwsalmon/grain`, and `old.yml` pulls
`ghcr.io/bwsalmon/grain/guest:latest` in a job with
`repo-read:gke-labs/granule`. Each read capability is justified by its
workflow's comment, and none is write-scoped, so INV-22 holds. Anyone
who can push to grain `main` or publish that image runs code with
granule read access during silo CI. That is T-TB9-1's accepted
residual; pinning the image by digest would narrow it.

## Checked and found sound

**Identity (TB1, INV-1)**
- `identity.Verify` takes the key from `kid` and the algorithm must
  match the key type (ES256/P-256 with a 64-byte signature, or RS256
  with ≥ 2048-bit RSA), so `none` and HMAC confusion are impossible.
- Issuer, audience (string or array), `exp` (required), `nbf` and `iat`
  are checked with 1 minute of leeway, plus the nonce on sign-in.
- JWKS are fetched with a 1 MiB cap, a 10 s timeout, at most one
  refetch per minute for an unknown `kid`, and a fallback to the cached
  key only when the provider is down.
- IAP reads only `x-goog-iap-jwt-assertion`. `x-goog-authenticated-user-*`
  and the grain-style user headers are never read. The audience must
  start with `/projects/`.
- OIDC uses PKCE S256, `state` compared in constant time, the nonce
  bound to the flow cookie, `email_verified` required, HMAC-SHA256
  cookies keyed per purpose (a flow cookie cannot pass as a session), a
  32-byte minimum key, and `HttpOnly`, plus `Secure` on https.
- Exactly one sign-on is enforced (`Config.auth`), and
  `-dev-user-header` is not set anywhere in `deploy/` (O-12 still
  open). The secrets come only from the environment.

**Authorization (INV-9, INV-10)**
- Every directory, tasks, live and nodeui handler authenticates first
  and answers 401 without a principal.
- Teams the caller is not in answer 404, while a team they are in but
  do not administer answers 403. That is consistent and leaks nothing
  new.
- A task invisible to the caller answers 404 in get, cancel, requeue,
  events and artifacts. `list` filters every row through `sees`
  whatever `team=` asks for.
- `submit` sets `Submitter` from the caller, and the strict decoder
  refuses `submitter`, `team` (for a repository task), `approved_by`
  and any unknown field. A repository task's team is the repository's
  current owner, never the body's.
- `manages` (cancel and requeue) requires the submitter, a team admin
  or a hub admin.
- `DELETE /v1/node-tokens/{id}` checks the owner and answers 404 for
  another owner's token. The body text differs from a missing token's,
  but IDs are 64-bit random. `GET /v1/node-tokens` is the caller's own
  (all for a hub admin).
- The node directory is filtered by `SeesNode` (O-9 unchanged).

**Node tokens (INV-6, INV-23)**
- 256-bit secret from `crypto/rand` and a 64-bit ID. The store holds
  only the SHA-256, and lookup is by hash in SQL, so there is no
  timing-sensitive comparison in Go.
- A unique partial index allows one live token per node, and minting
  revokes the owner's earlier ones.
- `revokeToken` disconnects the node. The mint response carries
  `Cache-Control: no-store`.
- The token binds the node ID: a hello naming another ID is refused,
  and `registry.ErrOwner` stops another owner while the hub remembers
  the ID (but see SA1-H1).

**Rendezvous (INV-2, INV-5, INV-19)**
- The node is authenticated *before* the WebSocket upgrade. No
  credential means 401 with no socket.
- The subprotocol is required. The hello is required within 30 s, and
  `acceptTimeout` closes a silent session.
- Control lines are ≤ 1 MiB.
- A superseding connection ends the old lease and session, and
  `Disconnect` closes the session.
- The `goodbye` and `welcome` messages carry no secret.

**Mux framing**
- Frames are ≤ 64 KiB (checked before allocation), the accept queue
  holds 256 streams (overflow is reset), and peer stream IDs are parity
  checked and never reused (`claimPeerID`, bounded memory).
- Frames for unknown or closed streams are dropped, and per-stream
  buffers reset on overflow. SA1-H2 covers the rest.

**Dispatcher (INV-7, T-TB5-5)**
- An offer re-checks admission against the task's repositories only.
- Store transitions are compare-and-set on `version`, so a cancel
  racing an accept resolves to one state.
- Only one stream is live per task (`d.live`). The dispatcher runs only
  under the `dispatcher` lease (a PostgreSQL advisory lock on its own
  connection, pinged every 2 s), and its 2 s window is accepted.
- Team-targeted tasks are offered only to nodes admitted for one of
  the team's repositories. `Constraints.Node` cannot widen placement,
  because it only narrows `ClaimFor`.

**Live (INV-3, INV-4, INV-8, INV-14)**
- `Classify` keeps lifecycle, conversation and token events only when
  they decode strictly against their schema with no extra field.
  Transcript tool fields reject the event, and result disk paths are
  cleared.
- Every other event becomes `{kind, ref, size}`, with `kind` by pattern
  and `ref` printable and ≤ 512 bytes. Token and node-only events go
  only to the bounded ring.
- An event stream binds to the first line's task, which must be on
  that node (but see SA1-H1), and a second task ends the stream.
- Artifacts are answered with `text/plain; charset=utf-8`, `nosniff`,
  `CSP: sandbox` and `no-store`, are streamed with a flush per write,
  and are written nowhere. INV-4's header assertion is still a test
  gap.
- SSE `event:` names are fixed types (unknown types became `artifact`).
  The data is JSON with no raw newlines, sent with `no-store`.
- The events WebSocket requires `Origin` host == `Host`, which also
  refuses node UI origins.

**Node UI (INV-13)**
- Only the node's owner is served (not hub admins), and anyone else
  gets 404.
- `Authorization`, the plaintext user headers and the hub's own
  cookies are stripped.
- A node's `Set-Cookie` with any `Domain`, or one that will not parse,
  is dropped.
- Upgrades must be same-origin. A node's answer line is ≤ 64 KiB.
- Hosts are DNS labels under the configured domain only, and node hosts
  never reach the hub's API mux.
- O-2 (the IAP assertion and IAP cookies passed through) is unchanged.

**Store**
- Every query is parameterised. The only built strings are fixed column
  lists, `?` lists sized by argument count, and an integer `LIMIT`.
- Migrations are `CREATE … IF NOT EXISTS` and nothing else.
- No row holds a secret except the token hash.
- Stored events are the classified, re-marshalled `Event`, never the
  raw line.

**Deploy**
- IAP is on the humans' backend. The IAP-off backend is an `Exact`
  match on `/v1/nodes/connect`, and the node UI hosts route only to the
  IAP backend.
- Metrics are on a port no Service names.
- Containers run non-root (but see SA1-L9), with no privilege
  escalation, a read-only root filesystem, all capabilities dropped and
  seccomp `RuntimeDefault`.
- Workload Identity binds the hub's KSA to a GSA with only
  `cloudsql.client` (see SA1-L8).
- The database URL is a Secret, Cloud SQL is `ENCRYPTED_ONLY` with no
  authorized networks, and backups and PITR are on. The IAP client
  secret is a Secret and is kept out of terraform state.

**CI (INV-22)**
- No workflow declares a write-scoped capability.
- `repo-read:bwsalmon/grain` (grain-interop) and
  `repo-read:gke-labs/granule` (old) are each justified by a comment.
- `hub-nightly` is schedule-only and needs no secrets.
- No step interpolates untrusted input into a script. The workflows
  have no `${{ }}` expressions at all.
- The gVisor download is checked against its sha512.

**Dependencies**
- The direct modules are pgx v5, prometheus client_golang, x/net,
  x/oauth2 and modernc sqlite. They are all well-known and need no new
  review beyond SA1-L4.
- govulncheck reports no reachable vulnerability in third-party modules
  besides the x/net HTTP/2 halves.
