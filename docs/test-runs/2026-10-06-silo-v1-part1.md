# Silo v1, part 1: thorough test run

**Date**: 2026-10-06 (task 2246)
**Commit tested**: `dcf028cdf` (`main` tip at the start of the run). Silo is
**not on `candidate`**: `candidate` (`8cf05de90`) carries only
`pkg/silo/facade/gce/filter`, so everything below was run from a
worktree of `main`.
**Environment**: Debian sandbox, Linux x86_64, 4 vCPU / 7 GiB, Go 1.26.6,
Debian's `postgresql` 15 (installed for the run), `gcloud` with the
task's `gcp-key` service account `grain-sb-agent-0@bsalmon-fun-sandbox`.

"Part 1" is taken to be everything Silo has landed on `main` so far (tasks
2022–2045): the store (SQLite and Postgres), the ledger (quota, address
space, root capacity), the GCE client and its fake, the fence compiler and
evaluator, the `silo/v1` fence API, the `compute/v1` facade (networks,
subnetworks, firewalls, reads, list filters), the gateway's origin identity
and Layer 1 control gate, `manage` grants, `silo install`'s planning and the
`silo` CLI. The facade does not serve instances, disks, images or templates
yet (`compute.instances.insert` is `403 method not allowed`), so those cases
in [`docs/silo/testing.md`](../silo/testing.md) were out of scope.

## Stubs

- **GCE**: the in-memory fake (`pkg/silo/gce/fake`) for every end-to-end
  call. To make that work, the run used a 25-line local program (not
  committed) that serves the fake's `Handler()` on `127.0.0.1:18090` with
  the host VPC `silo` already made, and pointed `silod serve
  --compute-endpoint` at it. See finding 2 for why `--fake-gce` couldn't be
  used.
- **Network**: origin identity used real source IPs. silod was bootstrapped
  with `address_space 127.0.0.0/8` (gateway range `127.255.255.0/24`, control
  range `127.255.254.0/24`), so every loopback address is in the tree, and
  each call was sent with `curl --interface 127.x.y.z` from the address of
  the silo it was meant to act as.
- Nothing else was stubbed. `silod serve`, `silod gateway`, the `silo` CLI
  and SQLite were the real binaries and store.

## 2. End to end: silod + gateway + CLI on SQLite

Setup: `silod serve --store sqlite:… --migrate --listen 127.0.0.1:18080
--gateway-socket gw.sock --host-project hp --compute-endpoint <fake>
--dev-caller-header`, then `silod gateway --silod-socket gw.sock --api-listen
127.0.0.1:18081`. The root was bootstrapped on the dev port. Every other call
went through the gateway on `:18081`. The root's subnet `127.0.0.0/24` made
`127.0.0.1` the root, so the `silo` CLI (`SILO_ENDPOINT=http://127.0.0.1:18081/silo/v1/`)
acted as `/`.

### What the service account can and can't do

`testIamPermissions` on the project:

- **Has**: compute networks, subnetworks, instances, disks, images,
  snapshots, instance templates, firewalls, network firewall policies and
  `setFirewallPolicy`, routers, addresses, forwarding rules, region and
  project reads, and `iam.serviceAccounts.actAs`.
- **Lacks**: `iam.serviceAccounts.create`, `iam.roles.create`,
  `resourcemanager.projects.getIamPolicy` and `setIamPolicy`,
  `dns.managedZones.create`, `cloudsql.instances.create`,
  `servicenetworking.services.addPeering`, `serviceusage.services.enable`,
  `cloudquotas.quotas.get`, `secretmanager.secrets.create` and
  `storage.buckets.create`.

So `silo install`'s apply (silod's account and role, the IAM grants, the
DNS zone, Cloud SQL and its PSC endpoint) and the root-capacity read from
Cloud Quotas cannot be tested with this key. The project is also shared
with the running grain deployment (`grain`, `grain-net` and others), so a
real install's fence policy must never be associated with any network but
its own.

## Findings

1. **The fence API's Postgres cases never run in CI.** `pkg/silo/fenceapi`
   has `TestPostgres` (14 cases, through `pgtest.Start`). The `go` job has
   no PostgreSQL, so it skips them. The `postgres` job runs only
   `./pkg/silo/store/...`. They pass when run by hand. Fix: add
   `./pkg/silo/fenceapi/` (and any later package that calls `pgtest`) to
   the `postgres` job's `go test` line in `.grain/workflows/tests.yml`.
2. **`silod serve --fake-gce` can't make anything.** The fake starts with an
   empty host project, so the host VPC `silo` doesn't exist, and every
   subnetwork insert fails with `The resource
   '…/networks/default' was not found`, even though `networks.list` shows
   `default`. The dev mode needs to make the `silo` network (as install
   would) when it builds the fake.
3. **`gcetest` can't run against real GCE as written**, though its package
   comment says it can:
   - each case gets one minute, and a real `stop`/`suspend` takes longer;
   - it assumes an empty project: `Lists` wants exactly one network,
     `FirewallPolicy` exactly one policy, and `us-east1-b` empty;
   - it uses fixed global names (`silo`, `silo-fence`, `img-1`, `tpl`) and
     never deletes the network or subnet it makes, so a second case fails
     with `alreadyExists` against real GCE;
   - nothing wires it to the real client. A harness gated on an env var
     (project, region, zone), unique per-run names, and a sweeper would
     make it the first piece of the conformance suite.
4. **The CLI can't reach a dev silod.** `silo` sends no `Silo-Caller`, so
   against `silod serve --dev-caller-header` every call is `no Silo-Caller
   header`. Outside the cloud the CLI only works through a gateway with the
   caller's source IP in the tree, as in this run. It's a dev-loop nit
   until the front door exists.
5. **The fake accepts two calls real GCE refuses.** `disks.update` with no
   `name` in the body (GCE: 400 `INVALID_FIELD_VALUE` on `resource.name`),
   which `gcp.Client.UpdateDisk` sends as written. The facade's planned
   `disks.update` support would fail against GCE until the client (or its
   caller) sets the name, and the fake should refuse it as GCE does. Also
   `instances.suspend` on the suite's e2 VM (GCE: `UNSUPPORTED_OPERATION`):
   the fake should model which instances may suspend, or the suite should
   use one that can.

## Permissions needed for the full test

To run [`docs/silo/testing.md`](../silo/testing.md)'s conformance suite
and a real `silo install` / `uninstall`, the task's service account (or a
dedicated one for the Silo conformance schedule) needs, in
`bsalmon-fun-sandbox` or better in a dedicated project:

- `roles/iam.serviceAccountAdmin` and `roles/iam.roleAdmin`, and
  `resourcemanager.projects.getIamPolicy`/`setIamPolicy` (for example,
  `roles/resourcemanager.projectIamAdmin`): install creates silod's
  account, its custom role and the admin grants.
- `roles/dns.admin`: the `silo.internal` private zone.
- `roles/cloudsql.admin`, plus Private Service Connect
  (`compute.forwardingRules`, already held) and
  `servicenetworking.services.addPeering`: the Cloud SQL instance and its
  endpoint.
- `roles/serviceusage.serviceUsageAdmin`: install's prereqs enable APIs.
- `roles/cloudquotas.viewer`: the root's capacity read.
- A **dedicated project** is strongly preferred. The suite asserts on
  whole-project lists, and a real fence policy in a project that also runs
  the grain deployment is a risk nobody needs.
- For a scheduled run: the deployment's CI capabilities in grain/config
  must grant `gcp-key` to that schedule (scheduled runs get no
  write-scoped capabilities today).
