# Hub fault and load run, 2026-10-16

The first run of the hub's fault-injection and load harness,
`hub/faulttest` (task 4241). Every number here comes from one 4-vCPU,
8 GiB grain sandbox. That one machine ran everything at once: the
PostgreSQL 15 server, the `silo hub serve` process, the 500 simulated
Grains and the 1,000 subscribers. So these numbers are a floor for what
the hub can do, not its capacity on its own node.

## The harness

- **The hub** is the real `silo hub serve` binary, built from the
  checkout. It runs as a child process, so the tests can send it
  SIGTERM or SIGKILL. It runs with `-heartbeat 1s` (so `StaleAfter` is
  3s) and `-dispatch-retry 1s`. Those two flags are new for these
  tests; their defaults are unchanged.
- **PostgreSQL** is a throwaway server (`internal/pgtest`). The hub
  reaches it through an in-process TCP proxy (`faulttest.Proxy`). The
  checks read the database directly, not through the proxy.
- **Grains** are simulated by `faulttest.Grain`, built on the real
  `rendezvous.Client.Connect`. Each one connects through its own proxy.
  It accepts each offer (or refuses it, if set to). It streams the
  task's events over time on an event stream of its own, then writes
  the result on the task stream. It behaves like a real node:
  - it keeps a task running when its connection drops;
  - on every new connection it replays the events of each task not yet
    delivered;
  - it reports a task's result again on every resume;
  - it serves an artifact view through the hub.
- **Fault controls.** Each proxy can be:
  - cut: every connection reset;
  - taken down: cut, and new connections refused;
  - black-holed: nothing forwarded and no close passed on, which is a
    half-open connection or an unannounced partition;
  - degraded: added latency, and a 200ms stall on a "lost" chunk.
- **What every scenario checks.** At the end, `Cluster.Settle` and
  `Verify` check that:
  - **no task is lost**: every submitted task is `done`;
  - **no task runs twice**: exactly one Grain started each task, once;
  - **seq only goes up**: each task's stored events are exactly the
    expected seqs, in order, ending in its result. Every subscriber
    also checks that each seq it sees (across reconnects with
    `Last-Event-ID`) is above the last one, and that it sees the end;
  - **the hub converges**: every Grain is online with no slot claimed,
    and no task is offered, running or lost.

## Fault matrix

`go test ./hub/faulttest` runs the short version on every pull request,
through hub.yml's `go test`. It took 147s under `-race`, the same as CI.
The nightly workflow `.grain/workflows/hub-nightly.yml` runs the full
version with `SILO_FAULT_FULL=1`.

### Bugs found, and fixed here

1. **Lost task transitions while the database is away.** When the
   dispatcher's store write failed (`Accept`, `Finish`, `Requeue`,
   `Lose`, `CancelDelivered`), it logged the error and dropped the
   write. A task whose `Finish` failed stayed `running` in the store
   for good, with no stream to end it. `Dispatchable` lists only queued
   and lost tasks, so no dispatcher pass ever looked at it again. A
   30s outage left 6 of 12 tasks stuck. The dispatcher now retries
   each transition with backoff (up to 5s) until it is written, or
   until the dispatcher stops; if it stops first, `Recover` handles the
   task on the next start (`hub/tasks/dispatch.go`, `record`).
2. **A Grain refused for good because the database was away.** The
   rendezvous server answered a failed admission check with a
   *refusal*. `rendezvous.Client.Run` never retries a refusal, so a
   real Grain reconnecting during an outage would have stopped
   permanently. The server now passes the directory's database errors
   back as `rendezvous.ErrUnavailable` and just closes the connection,
   which the client retries. It still refuses a node that is not
   admitted (`directory.ErrNotAdmitted`).
3. **Events a Grain could never know to replay.** The hub ended an
   event stream with the same close whether it had taken in every
   event or had failed to keep one (database away, stream refused).
   The hub writes nothing back on that stream, so a node had no way to
   tell the two apart. It would count its events as delivered, and the
   task ended with no stored events at all. The hub now *resets* any
   stream it ends for a reason other than the node's own clean end, and
   the node sees a reset as an error and replays
   (`hub/live/hub.go`, `NodeStream`).

### Seen but not fixed (follow-up tasks filed)

- **A subscriber can hang on a task that is over.** `upstreamClosed`
  checks whether the task has ended before ending its subscribers. If
  that read fails (the database is away) when the task's last stream
  closes, and the task's result event never arrived, the subscribers
  are never ended. Fix 3 makes this rare, because the node replays,
  but it is not impossible. Since fixed (task 4258): the hub reads the
  task again until it can, and the dispatcher tells the hub when a
  task finishes (`live.Hub.Finished`).
- **The slow subscriber was never dropped.** At this event size,
  loopback socket buffers absorb more than the hub's 512-event buffer
  ever holds. So the "drop and reconnect from the cursor" path was not
  exercised end to end, only checked not to stall the others.

## Load

`TestLoad` submits tasks round the teams at a steady rate. Each task
runs for a fixed time and streams status events, with 4 transcript
(token) events after each one: 1 in 5 events is stored, the rest go
only to the ring. Each of the first N tasks gets an SSE subscriber of
its own. The test checks the same invariants as the fault scenarios.

### Full size (nightly, `SILO_LOAD=1`)

Setup: 500 Grains (50 teams × 10, 4 slots each). Intake was 50 tasks/s
for 60s, 3,000 tasks in all. Each task ran 20s and emitted 201 events,
41 of them stored. 1,000 subscribers. The target is 10,050 events/s at
steady state.

The first run found the dispatcher slow (below). The second column is
the same run after the fixes of task 4257.

| Measure | First run | After task 4257 |
|---|---|---|
| Grains connected | 500 in 1.9s | 500 in 2.2s |
| Tasks done / lost / run twice | 3,000 / 0 / 0 | 3,000 / 0 / 0 |
| Events ingested | 603,000 over 92s, about 6,500/s on average; the average counts the ramp up and down | 603,000 over 81s, about 7,500/s on average |
| Dispatch latency, submit to offer at the Grain | **p50 4.0s, p99 11.8s**, max 12.5s | **p50 1ms, p99 3ms**, max 9ms |
| Fan-out latency, Grain write to subscriber read | p50 24ms, p99 1.6s, max 4.3s (39,955 events) | p50 1ms, p99 2ms, max 20ms (40,000 events) |
| Hub CPU | 0.46 cores during intake, 0.41 overall | 0.43 cores during intake, 0.39 overall |
| Hub memory | 535 MiB RSS at the end of intake, 653 MiB peak | 573 MiB RSS at the end of intake, 627 MiB peak |
| Database growth | 7 → 56 MiB: 16.6 KiB per task (123,000 stored events) | 8 → 55 MiB: 16.2 KiB per task |

### The first bottleneck: the dispatcher, and the pools under it

Dispatch latency climbed to seconds while the hub used less than half a
core. The event path kept up, with a fan-out p50 of 24ms. A rerun of
the first run's code gave p50 4.7s, p99 18.9s.

**What the profiles showed** (task 4257). A 30s CPU profile of the hub
during intake put the dispatcher at 2.6% of the hub's CPU. Most of the
CPU went to taking in events. So the dispatcher was waiting, not
working. Timing each pass showed what on:

- Reading the queue (`Dispatchable`) took 2–6ms, so re-reading it on
  every wake was not the problem.
- Under ingest, each `Offer` (a read, then an update) took 30–48ms on
  average, and each admission check (memberships, then the repository's
  owner) took 10–37ms. One serial pass over a few hundred queued tasks
  therefore took 3–10s.
- Those round trips were slow because of the connection pools. The
  hub's PostgreSQL pools had no cap, and `database/sql` keeps only 2
  idle connections. Every burst of event writes opened connections,
  each a new PostgreSQL process, and then closed them again. A goroutine
  dump caught 6 connections being made at one instant. At peak, the hub
  ran the server out of connections (`too many clients`, about 11,000
  times in one run). That made the dispatcher's writes fail and retry
  as well.

**What changed:**

1. **Each store's pool is capped and keeps its connections open**:
   `events` 32, `backlog` 16, `directory` 8, registry 8, and the notice
   bus 16 (hub-operations.md §5.3 has the per-replica total). This alone
   brought the full-size run to dispatch p50 1ms, p99 3ms, and fan-out
   p99 to 2ms, even with the old dispatcher.
2. **The dispatcher no longer makes serial round trips per task**:
   - each pass asks the directory once for each owner and set of
     repositories, not twice for every task;
   - the offer is one `UPDATE`, conditional on the version the pass
     read, instead of a read and then a write;
   - that write happens in the task's own goroutine, at most 16 at a
     time, so a pass only claims slots in memory.
3. **A registry change wakes a pass only if it may let a task be
   placed**: a node came online, or has more slots available than
   before. Heartbeats and claims no longer start a pass each.
4. **`Registry.forRepos` copies only the nodes that serve the task's
   repositories**, not all 500 entries for every task it tries.

Change 1 fixed this run. Changes 2–4 matter once the database is a
network round trip away, or intake outruns one serial pass. The load
test now has two knobs for that. `SILO_LOAD=burst` runs the same 500
Grains at 300 tasks/s, each task 4s long with 21 events (5 stored),
with 200 subscribers. `SILO_LOAD_DB_LATENCY=1ms` delays every chunk
between the hub and PostgreSQL by 1ms each way.

| Run | Pools capped, old dispatcher | All of task 4257 | Batched admission (task 4370) |
|---|---|---|---|
| Full size | dispatch p50 1ms, p99 3ms | p50 1ms, p99 3ms | p50 1ms, p99 5ms |
| Full size, 1ms each way to the database | dispatch p50 14ms, p99 22ms | p50 12ms, p99 15ms; fan-out p99 6ms | p50 12ms, p99 19ms; fan-out p99 7ms |
| Burst (300 tasks/s) | dispatch p50 2ms, p99 2.3s | p50 2ms, p99 2.2s | p50 3ms, p99 2.2s |
| Burst, 1ms each way to the database | dispatch **p50 21.3s, p99 39.8s** | **p50 441ms, p99 2.8s** | **p50 21ms, p99 2.3s** |

The old dispatcher made about four round trips per task, one task after
another. At 2ms a round trip, that caps it near 125 tasks/s, and the
burst's backlog grew without bound. In the burst without the added
latency, the p99 of about 2.2s is not the dispatcher's. A node's free
slots are only reported at its next heartbeat (every 5s here), so a
task that finished is not counted as free until then.

**Merging R4 (task 4264) made it worse first.** The rerun after merging
cross-pod wake-ups and live events was slower in two places:

- with 1ms each way to the database, fan-out fell to p50 1.0s, p99 22s;
- the latency burst fell to p99 7s.

Every stored event, every `Wake` and every heartbeat that moves a
node's free slots is now a `NOTIFY`, sent while its caller waits. They
went over the bus's pool of 4 connections, of which only 2 stayed idle.
The bus pool of 16, which keeps its connections, gives the numbers
above.

**Batching the admission checks** (task 4370). In the latency burst,
half of each pass was admission. The burst spreads over 50
repositories, so each pass made one directory check (two round trips)
for each one. Now a pass reads one `directory.Admission` the first time
it has a node to check. That read covers the memberships of every
registered node's owner and the owning team of every repository its
tasks may run in, in two queries. Every check in the pass is answered
from it. It is still read fresh each pass (hub.md §5.3), and a refusal
is the same `ErrNotAdmitted`, in the same words. The handshake's
`Admit` uses the same read, so it is also two round trips instead of
one plus one per repository.

The last column of the table above comes from one machine (4 cores,
PostgreSQL 15 local). On that machine, main at task 4257 gave:

- latency burst: p50 437ms and 528ms, p99 2.8s and 2.9s, in two runs;
- other three rows: within a millisecond or two of the branch.

Only the latency burst moved. Its p99 is now the heartbeat floor that
the burst without added latency already showed.

**Still open:**

- Every stored event is still one `NOTIFY`, sent while the node's
  event stream waits. At 2,000 stored events/s that is the bus's
  steadiest load. Batching notices, or sending them off the stream,
  would keep a slow bus from holding up ingest (follow-up task). Since
  fixed (task 4371), below.

**Notices off the stream (task 4371).** Ingest, `Wake` and the
registry no longer wait on the database for a notice. They queue it
(`notify.Bus.Post`). One goroutine a pod sends the queue every 2ms, or
when its last send returns, as one `SELECT pg_notify(...) FROM
unnest(...)`: one statement and one transaction a batch. While a notice
waits, a later one about the same thing replaces it: one wake-up, one
notice per node, and one per task carrying its highest seq. The bus is
back to 4 connections, now all kept open. Same machine, 1ms each way to
the database:

| Run | Bus of 16, a `NOTIFY` per event (task 4257) | Coalesced, off the stream, bus of 4 |
|---|---|---|
| Full size | dispatch p50 12ms, p99 15ms; fan-out p99 6ms | dispatch p50 12ms, p99 16ms; fan-out p50 4ms, p99 7ms, max 24ms |
| Burst (300 tasks/s) | dispatch p50 441ms, p99 2.8s | dispatch p50 516ms, p99 2.8s; fan-out p50 4ms, p99 19ms |

Hub CPU was 0.51 cores during the full-size intake (0.45 overall) and
0.85 during the burst. Peak RSS was 613 MiB and 263 MiB. Nothing was
lost, duplicated or out of order.

With 4 connections, a `NOTIFY` per event gave fan-out p99 22s. Coalesced,
the same 4 give 7ms. The 16-connection pool already matched these
latencies, so they are not the gain. The gain is that the bus's
statements no longer grow with ingest: at most one every 2ms (500 a
second) whatever the event rate, against a few thousand before. A slow
or stalled database now delays notices, not the streams that store
events. The burst's dispatch p99 is still admission's round trips, as
the first item above says.

Memory is the next thing to watch. About 1 MiB per Grain at peak points
at the mux's per-stream receive windows and the per-task rings (1,024
events / 1 MiB each). That is fine at 500 Grains, but it grows
linearly.

### CI size (every PR) and its regression thresholds

Setup: 50 Grains (5 teams × 10, 4 slots each). Intake was 10 tasks/s
for 20s, 200 tasks, each running 10s with 101 events. 100 subscribers.
The target is about 1,000 events/s.

| Measure | First run | After task 4257 (`-race`, as CI) | Threshold (`load_test.go`) |
|---|---|---|---|
| Dispatch latency | p50 3ms, p99 6ms | p50 2ms, p99 5–7ms | p99 ≤ 500ms (was 2s) |
| Fan-out latency | p50 4ms, p99 14ms | p50 1ms, p99 4–6ms | p99 ≤ 250ms (was 1s) |
| Hub peak RSS | 55 MiB | 64–67 MiB | ≤ 256 MiB (was 512 MiB) |
| Hub CPU | 0.12 cores | 0.10–0.12 cores | — (reported) |
| Database growth | 11.3 KiB per task | 9.3 KiB per task | — (reported) |
| Lost, duplicated or out-of-order | none | none | none (fails the test) |

The thresholds stay loose on purpose: about 100× the measured p99s, and
4× the peak RSS. A shared CI runner is noisy, and the failure modes
here are cliffs (seconds, not milliseconds), which these thresholds
still catch. The CI size does not reach either cliff found here,
though. Its 10 tasks/s never outran the old dispatcher, and its 50
Grains never ran out of connections. Only the nightly full size, and
the burst, would show them again.

## Running it

```sh
go test ./hub/faulttest                                     # the PR tier: short faults, CI-sized load
SILO_FAULT_FULL=1 go test -run 'Test[^L]' ./hub/faulttest   # the full fault matrix
SILO_LOAD=1 SILO_LOAD_REPORT=/tmp/load.txt go test -run TestLoad -timeout 25m ./hub/faulttest
SILO_LOAD=burst SILO_LOAD_DB_LATENCY=1ms go test -run TestLoad -timeout 25m ./hub/faulttest   # 300 tasks/s, database 1ms away
```

All of them need PostgreSQL's binaries (Debian's `postgresql` package).
Without them the tests skip, unless `SILO_REQUIRE_POSTGRES` is set.
