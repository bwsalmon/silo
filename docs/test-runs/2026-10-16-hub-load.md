# Hub fault and load run, 2026-10-16

The first run of the hub's fault-injection and load harness,
`hub/faulttest` (task 4241). Every number here comes from one 4-vCPU,
8 GiB grain sandbox. That one machine ran everything at once: the
PostgreSQL 15 server, the `silo hub serve` process, the 500 simulated
Grains and the 1,000 subscribers. So these numbers are a floor for what
the hub can do, not its capacity on its own node.

## The harness

- **The hub** is the real `silo hub serve` binary, built from the
  checkout. It runs as a child process, so the tests can send it
  SIGTERM or SIGKILL. It runs with `-heartbeat 1s` (so `StaleAfter` is
  3s) and `-dispatch-retry 1s`. Those two flags are new for these
  tests; their defaults are unchanged.
- **PostgreSQL** is a throwaway server (`internal/pgtest`). The hub
  reaches it through an in-process TCP proxy (`faulttest.Proxy`). The
  checks read the database directly, not through the proxy.
- **Grains** are simulated by `faulttest.Grain`, built on the real
  `rendezvous.Client.Connect`. Each one connects through its own proxy.
  It accepts each offer (or refuses it, if set to). It streams the
  task's events over time on an event stream of its own, then writes
  the result on the task stream. It behaves like a real node:
  - it keeps a task running when its connection drops;
  - on every new connection it replays the events of each task not yet
    delivered;
  - it reports a task's result again on every resume;
  - it serves an artifact view through the hub.
- **Fault controls.** Each proxy can be:
  - cut: every connection reset;
  - taken down: cut, and new connections refused;
  - black-holed: nothing forwarded and no close passed on, which is a
    half-open connection or an unannounced partition;
  - degraded: added latency, and a 200ms stall on a "lost" chunk.
- **What every scenario checks.** At the end, `Cluster.Settle` and
  `Verify` check that:
  - **no task is lost**: every submitted task is `done`;
  - **no task runs twice**: exactly one Grain started each task, once;
  - **seq only goes up**: each task's stored events are exactly the
    expected seqs, in order, ending in its result. Every subscriber
    also checks that each seq it sees (across reconnects with
    `Last-Event-ID`) is above the last one, and that it sees the end;
  - **the hub converges**: every Grain is online with no slot claimed,
    and no task is offered, running or lost.

## Fault matrix

`go test ./hub/faulttest` runs the short version on every pull request,
through hub.yml's `go test`. It took 147s under `-race`, the same as CI.
The nightly workflow `.grain/workflows/hub-nightly.yml` runs the full
version with `SILO_FAULT_FULL=1`.

| Scenario | Short (PR) | Full (nightly) | Result |
|---|---|---|---|

| Hub SIGKILL | 1 crash | 4 crashes | pass |
| One Grain partitioned (black-holed), shorter than `StaleAfter` | 1.5s | 1.5s | pass |

### Bugs found, and fixed here

1. **Lost task transitions while the database is away.** When the
   dispatcher's store write failed (`Accept`, `Finish`, `Requeue`,
   `Lose`, `CancelDelivered`), it logged the error and dropped the
   write. A task whose `Finish` failed stayed `running` in the store
   for good, with no stream to end it. `Dispatchable` lists only queued
   and lost tasks, so no dispatcher pass ever looked at it again. A
   30s outage left 6 of 12 tasks stuck. The dispatcher now retries
   each transition with backoff (up to 5s) until it is written, or
   until the dispatcher stops; if it stops first, `Recover` handles the
   task on the next start (`hub/tasks/dispatch.go`, `record`).
2. **A Grain refused for good because the database was away.** The
   rendezvous server answered a failed admission check with a
   *refusal*. `rendezvous.Client.Run` never retries a refusal, so a
   real Grain reconnecting during an outage would have stopped
   permanently. The server now passes the directory's database errors
   back as `rendezvous.ErrUnavailable` and just closes the connection,
   which the client retries. It still refuses a node that is not
   admitted (`directory.ErrNotAdmitted`).
3. **Events a Grain could never know to replay.** The hub ended an
   event stream with the same close whether it had taken in every
   event or had failed to keep one (database away, stream refused).
   The hub writes nothing back on that stream, so a node had no way to
   tell the two apart. It would count its events as delivered, and the
   task ended with no stored events at all. The hub now *resets* any
   stream it ends for a reason other than the node's own clean end, and
   the node sees a reset as an error and replays
   (`hub/live/hub.go`, `NodeStream`).

### Seen but not fixed (follow-up tasks filed)

- **A subscriber can hang on a task that is over.** `upstreamClosed`
  checks whether the task has ended before ending its subscribers. If
  that read fails (the database is away) when the task's last stream
  closes, and the task's result event never arrived, the subscribers
  are never ended. Fix 3 makes this rare, because the node replays,
  but it is not impossible. Since fixed (task 4258): the hub reads the
  task again until it can, and the dispatcher tells the hub when a
  task finishes (`live.Hub.Finished`).
- **The slow subscriber was never dropped.** At this event size,
  loopback socket buffers absorb more than the hub's 512-event buffer
  ever holds. So the "drop and reconnect from the cursor" path was not
  exercised end to end, only checked not to stall the others.

## Load

`TestLoad` submits tasks round the teams at a steady rate. Each task
runs for a fixed time and streams status events, with 4 transcript
(token) events after each one: 1 in 5 events is stored, the rest go
only to the ring. Each of the first N tasks gets an SSE subscriber of
its own. The test checks the same invariants as the fault scenarios.

### Full size (nightly, `SILO_LOAD=1`)

Setup: 500 Grains (50 teams × 10, 4 slots each). Intake was 50 tasks/s
for 60s, 3,000 tasks in all. Each task ran 20s and emitted 201 events,
41 of them stored. 1,000 subscribers. The target is 10,050 events/s at
steady state.

| Measure | Result |
|---|---|
| Grains connected | 500 in 1.9s |
| Tasks done / lost / run twice | 3,000 / 0 / 0 |
| Events ingested | 603,000 over 92s, about 6,500/s on average; the average counts the ramp up and down |
| Dispatch latency, submit to offer at the Grain | **p50 4.0s, p99 11.8s**, max 12.5s |
| Fan-out latency, Grain write to subscriber read | p50 24ms, p99 1.6s, max 4.3s (39,955 events) |
| Hub CPU | 0.46 cores during intake, 0.41 overall |
| Hub memory | 535 MiB RSS at the end of intake, 653 MiB peak |
| Database growth | 7 → 56 MiB: 16.6 KiB per task (123,000 stored events) |

### The first bottleneck: the dispatcher

Dispatch latency climbed to seconds while the hub used less than half a
core and the event path kept up: the fan-out p50 was 24ms. So the
bottleneck is not CPU and not ingest. It is the dispatcher's single
serial pass:

- Every pass reloads every queued task (`Dispatchable`).
- For each task it then makes several database round trips, one after
  another:
  - the team's repositories, for a team task;
  - `AdmitContext`'s membership and repository-owner queries;
  - `Offer`, which is a read and then an update.
- Passes are woken by every registry change. With 500 Grains
  heartbeating every 5s, that is about 100 wakes a second, and each
  wake re-reads the whole queue.

A backlog that builds faster than one pass drains it makes every pass
longer. The follow-up task has the work:

- batch admission (or cache it per owner for a pass);
- place more than one task per round trip;
- coalesce heartbeat wakes, since a heartbeat does not make a task
  placeable unless it frees a slot.

Memory is the next thing to watch. About 1 MiB per Grain at peak
points at the mux's per-stream receive windows and the per-task rings
(1,024 events / 1 MiB each). It is fine at 500 Grains, but it grows
linearly.

### CI size (every PR) and its regression thresholds

Setup: 50 Grains (5 teams × 10, 4 slots each). Intake was 10 tasks/s
for 20s, 200 tasks, each running 10s with 101 events. 100 subscribers.
The target is about 1,000 events/s.

| Measure | Result | Threshold (`load_test.go`) |
|---|---|---|
| Dispatch latency | p50 3ms, p99 6ms | p99 ≤ 2s |
| Fan-out latency | p50 4ms, p99 14ms | p99 ≤ 1s |
| Hub peak RSS | 55 MiB | ≤ 512 MiB |
| Hub CPU | 0.12 cores | — (reported) |
| Database growth | 11.3 KiB per task | — (reported) |
| Lost, duplicated or out-of-order | none | none (fails the test) |

The thresholds are loose on purpose, about 100× the measured values. A
shared CI runner is noisy, and the dispatcher's failure mode is a cliff
(seconds, not milliseconds), which these thresholds still catch.

## Running it

```sh
go test ./hub/faulttest                                     # the PR tier: short faults, CI-sized load
SILO_FAULT_FULL=1 go test -run 'Test[^L]' ./hub/faulttest   # the full fault matrix
SILO_LOAD=1 SILO_LOAD_REPORT=/tmp/load.txt go test -run TestLoad -timeout 25m ./hub/faulttest
```

All of them need PostgreSQL's binaries (Debian's `postgresql` package).
Without them the tests skip, unless `SILO_REQUIRE_POSTGRES` is set.
